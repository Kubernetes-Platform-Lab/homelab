# Ente database failover to `ente-postgres-restore`

Runbook for pointing Ente at a manually restored CloudNativePG cluster after
the primary `ente-postgres` cluster is lost.

Assumptions:

- `ente-postgres-restore` is a CNPG `Cluster` (pod `ente-postgres-restore-1`)
  that has completed recovery and is accepting connections.
- The original `ente-postgres` cluster is unrecoverable and will not be reused.
- ArgoCD auto-sync is disabled on `cluster-apps` and `ente`, so nothing changes
  until it is synced manually.

## 1. Restore db from cnpg backup and verify

Apply `cnpg-manual-restore-from-backup.yaml` file - remember to choose appropriate backup version. Wait for backup to completely restore (restoring WAL file can take up some time). After the restored cnpg cluster is restored you can proceed further.

Check which credential secret exists:

- `ente-postgres-restore-app` — generated by the operator; use it.
- only `ente-postgres-app` — recovery reused the source secret. Do **not** keep
  depending on it: it is owned by the old `Cluster` and will be
  garbage-collected when that cluster is deleted. Create a restore-cluster
  secret, or redo recovery with `database`/`owner` set so the operator creates
  `ente-postgres-restore-app`.

## 2. Point Ente at the restored cluster

Edit `04-argocd-apps/ente/application.yaml`:

```yaml
externalDatabase:
  host: "ente-postgres-restore-rw.ente.svc.cluster.local"
  port: 5432
  database: "ente_db"
  user: "ente"
  existingSecret:
    enabled: true
    secretName: "ente-postgres-restore-app"
    passwordKey: "password"
```

Apply and sync (the `ente` Application has no automated sync):

```bash
kubectl apply -f 04-argocd-apps/ente/application.yaml
```

Verify a real login/upload through `https://photos.akna.one.pl`.

## 3. Take the old cluster out of service

Only after the app works against the restore cluster:

```bash
kubectl -n ente patch cluster ente-postgres --type merge -p '{"spec":{"instances":0}}'
```

Before deleting it permanently, remove `04-argocd-apps/ente/ente-postgres.yaml`
from git (or replace it with the restore-cluster manifest). Otherwise a future
manual sync of `cluster-apps` would recreate an empty `ente-postgres` with
`initdb`.

## 4. Make the restore cluster a proper primary

The restore manifest has no `spec.backup`, so it is not backing up. Add a
distinct `serverName` so it does not write into the old cluster's WAL prefix:

```yaml
spec:
  instances: 2                # optional: restore HA
  backup:
    barmanObjectStore:
      destinationPath: "s3://ente-s3-backups/"
      endpointURL: "http://seaweed.akna.lan:8333"
      serverName: ente-postgres-restore
      s3Credentials:
        accessKeyId:
          name: ente-s3-backup
          key: accessKeyId
        secretAccessKey:
          name: ente-s3-backup
          key: secretAccessKey
      wal:
        compression: gzip
      data:
        compression: gzip
    retentionPolicy: "30d"
```

Update `ente-postgres-backup-schedule.yaml`:

```yaml
spec:
  cluster:
    name: ente-postgres-restore
```

Commit the updated `application.yaml`, the restore-cluster manifest, the
changed `ScheduledBackup`, and the removal of `ente-postgres.yaml`.

## Alternative: keep the original cluster name

Restoring in place is destructive and slower. It requires stopping ArgoCD from
managing `ente-postgres`, deleting the old `Cluster` and PVCs, adding
`spec.bootstrap.recovery` to `ente-postgres.yaml`, and re-syncing. The app
config does not need to change, but this is not recommended during an outage.

## Caveat

The restored cluster is at the last backed-up WAL position. Any writes after
that point are lost. If the old primary is still reachable, hibernate it before
switching to freeze writes, or explicitly accept the RPO.
